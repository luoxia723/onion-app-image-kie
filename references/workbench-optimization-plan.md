# 洋葱广告图工作台整体优化方案

日期：2026-11-02。状态：已实施。2026-11-02完成队列、状态、历史与草稿、轻量读取及执行模块整理；原数据保留。验证使用隔离模拟数据，未新增付费生图。

面向同一台电脑上的内部使用：多窗口操作、多任务排队、在线规划与生图、本机图片处理和保存。不同电脑分别安装，各自管理队列。目标是让用户清楚知道当前阶段、操作影响和结果位置，同时收敛执行逻辑与维护成本。

## 1 保留的产品与技术基础

继续使用原生 HTML/CSS/JavaScript、一个 Python 本机后台、SQLite 和本地文件。保留现有双击启动方式、Pillow/OpenCV、GPT Image 2 与 GPT Image 2.5 Sunburst 的 KIE 对接，以及固定1K输出。规划使用现有已配置API。

单图、双图、三图分别使用对应文案，允许分发到兼容的多个版位。模型、素材、画风和文案按制作轮次冻结。人工提示词可以自由修改、换行、删除系统句式，仅检查非空及接口允许的长度。视觉由用户挑选，文件规格由程序检查。

此次优化以现有能力为基础，不把账号、多人权限、云端同步或远程部署加入本轮范围。网页不负责维持队列，关闭网页后本机后台继续运行。

## 2 页面与入口

保留三个主要工作区域，不另建复杂管理台。

| 区域 | 内容 | 用户的主要操作 |
|---|---|---|
| 配置生成 | 图片形式、文案、版位、套数、模型、必要素材与要求 | 保存草稿、开始生成、提交新轮次 |
| 挑选保存 | 生成进度、版位套图、单张预览、提示词编辑 | 预选、重出、处理尺寸、保存图包 |
| 历史与交付 | 轮次摘要、旧图片版本、交付记录及保存位置 | 查找、查看原配置、下载副本、打开文件夹、归档 |

侧栏保持四组：草稿、正在处理、待处理、历史。待处理承接待挑选、待尺寸处理、需恢复查询及停止后的未完成任务，使用标签说明具体情况。每个任务只出现一次；只要任一轮仍有执行中的工作，任务保留正在处理标记。当前轮已经保存但仍有新选择或新编辑时，不将它表现成全部完成。

日期、模型、图片形式、关键词作为搜索或筛选条件。保存图包不要求覆盖所有版位；覆盖率是信息，不是错误。

### 新建与再次提交

提交前展示实际范围，例如：真实生图、GPT Image 2、1K、2个版位、每版位3套、共12张。沿用有依据的数量，不编造费用或剩余时间。

区分三类提交：同一份提交标识返回原任务；同配置新增版位或套数只补缺少部分；改变文案、模型或主要视觉要求则建立新轮次。新轮次展示“将新建第N轮，原结果保留”。旧轮已提交的供应商任务仍按原回执完成查询；旧轮尚未提交的图片不再继续提交。

## 3 统一状态表达

执行状态、挑选状态、交付状态分别保存，再组合成界面文字。不能只用一个“完成”判断全部业务。

| 所处阶段 | 显示内容 | 操作规则 |
|---|---|---|
| 待规划或正在规划 | 规划队列或正在规划画面 | 可以离开页面；不重复规划 |
| 待提交 | 排队中 | 不占生图并发名额 |
| 依赖未就绪 | 等待本套首图 | 不提交后续图，不当成独立生成失败 |
| 参考上传 | 正在上传参考图 | 使用真实上传阶段；不伪造百分比 |
| 供应商已接收 | 正在生成，显示本次执行已用时 | 保存任务号，继续查询 |
| 已有结果 | 正在下载或处理尺寸 | 保留原图，完成客观规格检查 |
| 生成完成 | 可以预览和挑选 | 不等于已保存图包 |
| 文件待处理 | 已生成，待尺寸处理 | 本机重新处理；不自动调用生图 |
| 查询未完成 | 暂未取得结果或需要恢复查询 | 查询原任务；不自动重复提交 |
| 确认失败 | 说明失败及可用操作 | 根据错误类型重试规划、上传或本张 |
| 暂停后续 | 已暂停后续提交，注明仍在运行的数量 | 已提交任务继续；恢复后继续原队列，不新增图片版本 |
| 停止后续 | 未提交部分已停止 | 保留结果和回执；重新生成由用户明确发起 |

顶部只显示当前最重要的信息，例如“已完成10/12张 · 正在生成1张 · 等待首图1张”。不要给没有依据的预计完成时间。

失去本机连接时显示“当前显示上次进度”，不能继续承诺后台仍在运行。连接恢复后自动同步。首次生成及运行期间清楚说明可以关闭网页，但需要保持本机服务和电脑运行。

等待、重试、恢复查询均有独立语义。没有任务号的提交不确定状态不能自动重新提交，需要先核对供应商记录。

## 4 编辑与图片版本

预览保持大图、实际参考图、有编号的提示词和本张操作。参考图编号严格对应实际请求顺序，文字编辑不会悄悄更换素材。

提示词区区分：当前图片使用的原始提示词、尚未生成的编辑草稿、新图片版本。编辑草稿自动保存在本机，并显示“草稿已保存，尚未生成”；关闭预览后可继续编辑。放弃草稿不调用API。

人工编辑与系统自动组装分开检查。系统组装需要检查输入完整和参考职责；人工编辑不能被系统固定句式、确认文案匹配或单段格式拦截。实际参考文件、版本依赖、模型和请求记录仍由程序管理。

| 操作 | 影响范围 |
|---|---|
| 重出图2或图3 | 只建立本张新版本，引用同套当前首图的确定版本 |
| 重出首图 | 建立首图和后续图的新版本；后续等待新首图完成 |
| 修改模型或确认文案 | 新建制作轮次，不改写原轮次 |
| 恢复查询 | 原请求、任务号、提示词和素材不变 |
| 本机去框或整图适配 | 保留原图，更新处理结果；不调用生图 |

新首图的后续图不得继续使用旧首图。旧版本文件保留，但退出当前可交付结果。恢复或采纳历史图片时必须检查整套依赖，不能拼出来源不一致的套图。

已经停用但属于历史图片的素材，显示“历史参考 · 已停用”。新任务不随机抽取它；历史预览与恢复仍可使用原文件。历史参考文件仍可用于恢复和重试，不能仅因素材停用就删除。

## 5 挑选与保存

继续以具体版位上的一套图片为预选单位。全选仅作用于当前渠道与筛选范围，并显示范围和数量。允许生成中预选，但保存时校验图片完整、版本一致、文件规格合格。

底部固定显示已选、可保存、待处理套数和覆盖版位。选中项有部分尚未就绪时，可以明确保存可交付部分，保留原勾选，告知本次未纳入哪些套图。未选版位不会成为保存障碍。

保存显示“正在保存图包”；只有后台实际提供阶段时，才进一步展示整理或打包进度。成功后保留版本、套数、图片数、文件位置，以及打开文件夹、下载ZIP副本两个入口。相同内容复用图包，新内容建立版本，不覆盖旧包。

本机工作区的ZIP和浏览器下载的副本要区分。图包保存成功不等于浏览器下载副本已经完成。

## 6 历史与清理

三个概念使用不同名称：制作轮次（第N轮）、图片版本（图N第M版）、图包版本（vNNN）。轮次列表展示编号、模型、图片形式、创建时间；可附“修改了模型”等简短变化摘要，不只写本轮或上一轮。

第一阶段支持查看历史轮次、旧图片及其实际提示词和参考图。之后再增加同版位对比和依赖正确的历史版本采纳，避免先做复杂对比编辑器。

历史保留规则：

- 默认保留任务摘要、配置、图片版本信息和交付索引，不因已保存满7天自动删除记录。
- 归档只改变列表显示，仍可搜索和取消归档，不删除文件或中止工作。
- 默认缓存清理只处理确定不再使用的临时文件和过期上传缓存，不动仍被草稿、图片版本、运行任务或套图依赖引用的文件。
- 清理原图等会影响重试或历史操作的内容，单独展示范围、预计空间和将失去的能力，用户明确选择后执行。
- 删除任务时明确记录、候选图片和交付包分别是否删除，不能混在“立即清理”里。
- 原图被清理但保留预览时，明确标记，不能继续展示需要原图才能完成的操作。

已有工作区路径、任务ID、图片版本和图包名称继续有效，不在本次升级中搬迁用户文件。

## 7 轻量后台设计

保持单个本机服务，内部收敛为任务管理、统一调度、API执行、图片处理与交付四部分。HTTP入口只负责读写请求和返回结果；执行逻辑不依赖网页打开。

### 队列

调度单位为一张图片的一个版本；首图依赖绑定到确定的版本和原始PNG。一个规划名额，图片生成共享全局上限。新安装默认并发4，已有用户设置保留；后续调整全局生效，降低额度不会中断已提交任务，只限制新提交。

不同任务轮流取得名额；同一任务内优先处理已经满足依赖的图片。等待规划、等待首图、暂停的任务不占生图名额。暂停、继续和停止不得通过创建新图片版本实现。

API等待、下载、OpenCV处理和打包在锁外执行；锁内只读取快照、领取任务、更新状态和确认结果。提交、结果和保存使用稳定的版本及操作标识，防止多窗口重复动作。

### 状态与模块

SQLite保存业务状态和索引，规划及配置可继续用JSON保存。执行状态只通过统一的任务更新入口推进；工作进程回执用于恢复和审计，不能与另一套内存状态各自决定结果。

保留原有回执恢复路径，先核对任务号、请求指纹和结果文件，再决定恢复查询。为新数据增加必要的版本字段即可，不引入ORM或为每个规划字段拆表。

模型标识、1K策略、可用画幅和参数差异集中在一个模型配置模块；界面选项由后台提供。素材可用状态也集中维护。前端重复函数逐步收敛，保留原生JS。

图片执行器暂时保持独立进程，受全局并发上限约束。先将KIE的提交、查询、下载和缓存从CLI脚本中整理成无临时全局替换的调用模块，再根据实际内存和维护成本决定是否调整执行方式。

### 界面数据

- 任务列表只获取名称、分类、进度、模型、缩略图地址和更新时间等摘要，不携带所有历史轮次与提示词。
- 当前轮次按需读取图片状态；预览打开后再获取完整提示词、参考图与版本信息。
- 后台返回修订号，未变化时避免重复传输详情和整页重建；隐藏或空闲窗口降低轮询频率。
- 编辑草稿使用修订号防止多窗口覆盖。冲突时保留本窗口内容，并提示重新同步或另存。
- 全局队列概览放在现有页面：运行数、等待数、暂停数即可。

## 8 实施顺序与验收

| 批次 | 完成内容 | 验收重点 |
|---|---|---|
| 第一批 任务状态与历史保障 | 备份与兼容读取；统一执行状态；冻结依赖版本；归档与缓存清理分离 | 历史图包可打开；旧回执可恢复；不再按7天删除任务记录；升级不重提生图 |
| 第二批 调度与数据读取 | 全局并发、任务轮转、暂停继续；列表摘要与按需详情；耗时工作移出锁 | 多窗口共享上限；大任务不长期占满；同一操作不重复提交；保存图包不阻塞队列 |
| 第三批 日常使用闭环 | 侧栏分类、真实阶段提示、提示词草稿、操作范围说明、保存反馈、历史入口 | 关闭重开可继续编辑；新旧版本可辨认；未选版位不阻止保存；人工内容原样执行 |
| 第四批 维护收敛 | API调用模块、统一模型配置、前端重复实现整理；历史对比按需要补充 | 行为不变、测试覆盖真实流程、打包和双击启动方式不增加依赖 |

每批先验证再切换，不同时重写所有模块。数据库变更前建立可恢复备份，迁移保留旧字段和回执；新旧读取行为逐步收敛后再移除兼容代码。

主要自动验收场景：多个窗口同一草稿只形成一次提交；不同任务共享全局额度；修改模型形成新轮次；各分支引用正确首图版本；人工提示词自由编辑及恢复；已提交任务超时只查询原任务；部分套图保存；历史归档与清理保护；服务重启和网络断开后的恢复。

开发验证使用隔离数据和模拟供应商，不影响当前任务。需要真实API验证时，范围限定到明确的最少图片数，并单独记录实际回执，不以静态测试宣称视觉质量已提高。

## 9 本轮完成标准

用户可以在多个窗口管理独立任务，理解真实加载状态，离开并返回，保留编辑草稿，按张重出且不混用首图，保存完整合格的预选套图，找到历史配置和交付物，清理空间时知道影响范围。

开发侧仍是一个启动入口、一个本机服务、一份SQLite和本地文件，依赖清单与现有平台启动方式保持轻量。
